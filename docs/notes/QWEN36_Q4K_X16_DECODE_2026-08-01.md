# Qwen3.6 Q4_K x16 decode promotion

## Outcome

Qwen3.6 decode now reuses the AVX-512 VNNI x16 Q4_K representation that the
generated prefill graph prepares at model load.  Decode previously ignored
that allocation and lazily built an x8 representation of the same weights.

There is no new selection flag.  The dispatcher selects x16 only when all of
the following hold:

- the CPU exposes the certified x16 provider;
- the projection has one of the measured Qwen3.6 shapes; and
- model initialization already prepared that weight in x16 layout.

Otherwise the existing x8 provider remains unchanged.  The lookup also
supports a 16-row-aligned view into a prepared tensor.  This lets the two
N=17408 decode calls reuse the single N=34816 gate/up allocation without a
second repack.

## Measurements

Host: Intel Xeon Gold 6542Y, 14 quota-matched threads, ICX AVX-512 build,
Qwen3.6-27B Q4_K_M, temperature zero, thinking suppressed.

The production-shape isolated sweep compared x8 and x16 with byte-equal
outputs:

| N | K | x8 ms | x16 ms | speedup |
|---:|---:|---:|---:|---:|
| 6144 | 5120 | 0.2770 | 0.1553 | 1.78x |
| 12288 | 5120 | 0.4520 | 0.2144 | 2.11x |
| 17408 | 5120 | 0.6605 | 0.4707 | 1.40x |
| 5120 | 6144 | 0.2600 | 0.2370 | 1.10x |
| 5120 | 17408 | 0.6920 | 0.4953 | 1.40x |

N=1024 regressed and is deliberately excluded.

In a controlled 33-token prompt plus 64-token decode A/B, median decode
latency fell from 310.88 to 266.31 ms/token (14.3%).  Median throughput rose
from about 3.22 to 3.76 tokens/s (16.8%).  A later no-selection-flag run under
lighter host load reached 4.19 tokens/s; it is evidence that automatic
selection works, not a cross-run speedup claim.

## Numerical and regression evidence

- The persistent llama.cpp trajectory oracle matched 32/32 generated
  positions for the 33-token prompt.
- A 1,000-token prefix matched 8/8 generated positions.
- The full prompt produced the same coherent C/Python/SQL answer prefix.
- `tests/test_q4k_llama_performance_gate.py`: 10 passed.
- `make test-threadpool-parity-quick`: all 12 groups passed.
- The production ICX model/runtime build passed.

The repository's direct `test-q4k-q8k-llama-packed-quick` target could not be
built in this checkout because its expected in-tree `llama.cpp/ggml/include`
headers are absent.  The persistent trajectory helper used the available
llama.cpp runtime successfully, so independent real-model oracle coverage was
still exercised.

## Q6 status

Q6 decode was measured before changing production.  Its current dispatcher is
already the parallel AVX2 provider: at Qwen3.6 shapes it was roughly 4-9x
faster than the serial path.  Replacing it safely requires a separately packed
multi-output AVX2/VNNI provider; the existing experimental AVX-512/VBMI path
does not satisfy the llama.cpp arithmetic contract and is not promoted by this
change.
